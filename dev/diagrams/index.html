The layers¶

Figure description and sources

Top to bottom, each arrow is a call. Your application calls one object, whose public calls are listed from the umbrella header in inc/. The core turns each call into register reads and writes and hands them to the port contract (the CRTP base in inc/*_interface.hpp), which forwards them, at compile time, to the hooks of the port class you write; your port moves the bytes on the bus. The notes on the right say which layers stay the same on every MCU and which one you write. A library without a port contract has only the first two layers.

ECKey session: opening it¶

Figure description and sources

The driver's eckey layer, the crypto port and the IoT applet. The driver first reads the chip's ECKA public key with an attested ReadObject and verifies the attestation. The crypto port makes a fresh ephemeral P-256 key pair for this session only and signs the request with the host's long-term key, whose public half is the ECKey authentication object on the chip. ECKeySessionInternalAuthenticate (84 88) carries the parameters (tag A6), the ephemeral public key (tag 7F49) and the signature (tag 5F37). The chip answers a 16-byte challenge and a 16-byte receipt. The host computes the shared secret, derives the master key (the first 16 bytes of SHA-256 over a counter, the secret, the chip's random and the parameters) and the session keys by CMAC, and checks the receipt in constant time before it trusts the session. The ephemeral private key and the master key are wiped. AN12543 pp. 22-23, 33-34, 72-73; no vector confirms the derivation yet, so it is built behind a flag.

Irreversible operations: plan, confirm, apply¶

Figure description and sources

Left to right. The build must define SE05X_ENABLE_IRREVERSIBLE, or none of these calls exists. The caller asks irreversible::Operations for a Plan of one operation: the Plan sends nothing, checks the arguments, the capabilities and the role, and says what will change. The caller shows the Plan to a person and builds a Confirmation of the same operation from its phrase. Apply() takes both; a Plan of another operation, a phrase of another operation or a Plan that was not prepared is refused before any byte is sent (Error::IrreversibleNotConfirmed). The operation tags are read from inc/se05x_confirm.hpp; the two PERSO operations live on perso::Perso and follow the same flow.

Lifecycle settings and the roles that change them¶

Figure description and sources

The device-wide settings of the IoT applet, each changed by one command that the chip accepts only in a session opened with one reserved authentication object (the AuthRole of inc/se05x_lifecycle.hpp, checked by RequiredRole() before anything is sent). Transport lock: SetLockState from a Transport session; while locked the chip answers only GetVersion, ReadState, the read of the unique id, GetRandom and CreateSession (AN12543 Table 19); the persistent lock survives resets and is lifted only from a Transport session again. Platform SCP required: SetPlatformSCPRequest from a PlatformScp session; from then on every command needs full platform SCP03. Restricted object creation: DisableObjectCreation; the persistent form cannot be undone. Applet features: SetAppletFeatures from a Feature (ECKey) session. Factory reset: DeleteAll from a FactoryReset session removes every object except the provisioned ones; its reply is not wrapped and the session ends. ReadState reads the first three at any time. Red arrows are the operations the driver treats as irreversible: they exist only with SE05X_ENABLE_IRREVERSIBLE and need a Plan and a Confirmation.

Objects, policies and sessions¶

Figure description and sources

Every key or data item on the chip is a secure object: a 4-byte identifier, a class (ObjectClass of inc/se05x_ids.hpp), a lifetime (persistent, or transient: the content is lost at reset or deselect) and an origin (generated inside, written from outside, or provisioned by the vendor; attestation reports it). At creation the object gets a policy set: each policy names one authentication object and the operations it may do (the Rule enumeration of inc/se05x_policy_types.hpp, 9 to 53 bytes per policy; AN12543 Table 63). An authentication object is itself a secure object (a UserID, an AES key or an EC key); a session opened with it (at most 2 at a time) is what a policy checks. The policy builder only builds rules valid for the class and generation, and the facade uses the strict profile only.

Device certificates: provision once, verify at boot¶

Figure description and sources

Left to right, top row once in the factory, bottom row at every boot. 1. The chip generates the key pair; only the public key comes out (ReadPublicKey). 2. BuildCsr writes the request and the chip signs its digest (DeviceSigner); VerifyCsr checks it against its own key. 3. The CA, outside the driver, issues the certificate. 4. StoreCertificate writes the certificate and the CA certificate (the trust anchor) into new binary objects with read-only policies, in one WriteBinary each, and reads them back. At boot: ReadCertificate and LoadTrustAnchor read them, VerifyChain checks signature, names, time, constraints and path length with the caller's clock, and the verified key is the chip's own. The CA, revocation and TLS are outside the driver.

The recovery ladder¶

Figure description and sources

When an exchange fails the link climbs these rungs in order, read from the Rung enumeration in inc/se05x_t1.hpp, and stops at the first that works. Each rung is bounded and is never repeated without limit. Resending the last block keeps everything. A resync and an interface soft reset keep the chip's state but drop the exchange in progress. Selecting the applet again closes the applet sessions. The chip reset (the NXP-flavour S-block 0xC6, or the reset port in the GP flavour, where 0xC6 means RELEASE) also clears transient objects, and is the only answer to SW 0x66A6. The power cycle needs the reset port (ENA with VOUT wired to VCC on the SE050 and SE051) and is the only cure for errata I2C.1. After any rung past the resend, the driver forgets every session and the caller authenticates again (Error::Resynced).

Platform SCP03: opening the channel¶

Figure description and sources

Three parties, left to right: the driver's scp03 layer, the crypto port that holds the static platform keys as handles, and the chip's card manager. The driver sends INITIALIZE UPDATE with a host challenge; the chip answers with its challenge and card cryptogram. The crypto port derives the session keys from the static keys (the driver never sees them) and the driver checks the card cryptogram in constant time. EXTERNAL AUTHENTICATE carries the host cryptogram and the security level; when platform SCP is required the level must be full C-MAC, C-ENC, R-MAC and R-ENC (AN12543 SetPlatformSCPRequest, p. 75). Every later APDU is wrapped (C-MAC, C-ENC) and every reply checked (R-MAC, R-ENC); a failed check closes the channel and wipes the keys. The normative SCP03 text is the GlobalPlatform SCP03 amendment, which is not in this driver's source set: the byte detail follows AN12543 p. 72 and the middleware oracle.

Figure description and sources

Wiring the SE052¶

Figure description and sources

The SE052 on an MCU's I2C bus. SDA (pin 11) and SCL (pin 10) go to the MCU with pull-ups to the bus supply of 1.65 V to 3.6 V, which also feeds VIN (pin 12). VOUT (pin 15) goes to VDD (pin 18) on the board, as Table 2 asks; Figure 1 shows an optional 22 nF on VIN and an optional 22 nF (or nothing) on VOUT. RST_N (pin 14) goes to a GPIO the reset port drives low to reset the chip. There is no ENA pin: deep power-down is the S-block 0xDF, and the next I2C access wakes the chip. CLK (13) is left open or tied to ground, LA and LB are left open, IO1 and IO2 are the chip's own I2C controller and stay open when it is not used. The pull-up value is not in the data sheet.

One T=1 block on the bus¶

Figure description and sources

One block on the I2C bus, in the order its bytes are sent, for each flavour the driver speaks. The NXP flavour (UM11225) has NAD 0x5A from the host and 0xA5 from the chip, a one-byte LEN and at most 254 bytes of INF. The GlobalPlatform flavour (GPC_SPE_172) has NAD 0x21 and 0x12, a two-byte big-endian LEN and up to 4089 bytes of INF. Both end with a CRC-16 over NAD to INF; in the GP flavour it is CRC-16/X-25 sent most significant byte first (the document's example block ends in BDA4); UM11225 gives neither the polynomial's byte order nor an example, so the link tries both orders and keeps the first that checks. The PCB byte tells the three kinds of block apart. Every number is read from inc/se05x_wire.hpp.

The T=1 link: states and S-blocks¶

Figure description and sources

Each box is a LinkState of t1::Link, read from inc/se05x_t1.hpp. Open() reads the ATR or CIP and selects the applet, leaving the link Idle. A command makes it InFlight: one I-block per I2C write (chained when the APDU is longer than IFSC, each part acknowledged by an R-block), then the reply is polled. While in flight the chip may ask for more time with S(WTX request), which the link answers with S(WTX response), counted against Config::wtx_limit; a bad block gets an R-block and is resent at most Config::frame_retries times. A reply returns the link to Idle. A rung of the recovery ladder that resets the chip's context leaves NeedsReselect, which selecting the applet again ends; when the ladder is spent the link is Dead and only Close() and Open() start it again. The S-block codes are the ones of inc/se05x_wire.hpp; 0xC6 is a chip reset in the NXP flavour and RELEASE in the GP one.

Trust boundaries¶

Figure description and sources

Three zones from right to left. Inside the chip: the private keys, the policies, the counters, the RNG and the attestation key; the chip enforces every access rule. The bus between host and chip carries APDUs in clear unless a secure channel (platform SCP03, an AESKey or an ECKey session) wraps them; anyone with a probe on SDA and SCL sees and can inject plain traffic. The host MCU runs this driver, which is a courier: it holds no long-term secret except the platform SCP03 keys, and those only as handles in the crypto port. The verifier, far left, checks attestations and signatures with public keys only. Each arrow says what crosses the boundary.

Choosing a variant, an applet and an authentication¶

Figure description and sources

Read top to bottom; take the first question you answer yes. Certification needs come first: FIPS 140-3 Level 3 is the SE052F; FIPS 140-2 with SCP03 mandatory is the SE050F. Then interfaces: NFC commissioning and Matter (PAKE) is the SE051H, UWB the SE051W. Field update of the applet (SEMS Lite) is the SE051A or C. Otherwise the SE050 by algorithm set: E for AES-GCM and CCM and Curve448 (applet 7.x), C for ECC and RSA, A for ECC only, B for RSA only, D for ECC with MIFARE DESFire. The SE051P runs a customer applet and has no IoT applet, so this driver does not apply. The bottom row is the authentication choice: platform SCP03 whenever the bus can be probed, an ECKey session to bind a host, a UserID session only under a trusted host OS, since it has no secure messaging. The driver reads the real capabilities at Open() and never trusts the part name.

SE05X Driver¶

A C++20 driver and hardware root-of-trust facade for the NXP EdgeLock SE050, SE051 and SE052 secure elements: T=1 over I2C, SCP03, the IoT applet, typed objects and policies, attestation and guarded irreversible operations, on any MCU.

Choose your job The first 15 minutes API guide Source on GitHub

The SE05x is a family of secure elements (SE050, SE051, SE052) that hold keys and credentials isolated from the host, sign, agree keys and attest with them inside the chip, and talk to the host over I2C with T=1 framing and an encrypted SCP03 channel (SE050 1 Introduction, p. 1).

The three chips differ in package, applet, memory and certification: Where to use it helps you choose and draws the SE052's HVQFN20 package; the figures below show the HX2QFN20 of the SE050 and SE051.

Where it is used¶

  • Secure connection to public and private clouds and edge platforms
  • Device-to-device authentication
  • Protection of data such as sensor data (SE050 1 Introduction, p. 1)
  • Wi-Fi credential protection: a device key for WPA-EAP-TLS (AN12661 2 Wi-Fi credential protection, p. 4)
  • Secure commissioning, key storage and credential provisioning
  • Ecosystem protection
  • Smart industry, smart home, smart cities and smart supply chains (SE050 1.2 SE050 target applications, p. 2)
  • Healthcare (SE052) (SE052 1.2 Applications, p. 1)

Uses named by the datasheet (SE050 1.1 SE050 use cases, p. 1).

Quick start¶

Wire the chip as above, write the port for your MCU (Porting), then:

using BoardPorts = se05x::Ports<MyBus, MyClock, se05x::ReferenceCrypto>;

se05x::Error RandomBytes(MyBus& bus, MyClock& clock, se05x::ReferenceCrypto& crypto,
                         se05x::MutableByteSpan out) noexcept {
  const BoardPorts ports(bus, clock, crypto);
  se05x::Device<BoardPorts> device(ports, se05x::Config{});
  if (const auto opened = device.Open(); !opened.ok()) {
    return opened.error; // for example DeviceIdMismatch: nothing answered like an SE05x
  }
  const auto random = device.GetRandom(out);
  static_cast<void>(device.Close());
  return random.error;
}

The driver has no platform code. You give it small port classes (a bus and a clock, optionally reset and a hardware crypto engine); it does the framing, the secure channel, the checks and the recovery.

What it does for you¶

  • Provision

    Keys generated inside the chip, under a strict policy, in one call.

  • Attest

    Prove a key or a value came from this chip; fresh, verified, typed.

  • Sign and verify

    ECDSA, and EdDSA except on the SE052F in FIPS mode (variants), with keys that never leave the chip.

  • ECDH

    Key agreement with the secret kept on the chip.

  • Key import

    Wrapped import under a key-encryption key; no plain key on the host.

  • Secure channels

    Platform SCP03, AESKey and ECKey sessions; no half-open channel.

  • Secure storage

    Binary objects whose policy decides who reads them.

  • Certificates

    Read the provisioned certificates, store your own.

  • Counters

    Monotonic counters and anti-rollback floors.

  • Lifecycle and lock

    Transport lock, SCP requirement, factory reset; irreversible steps guarded.

  • Security model

    What the chip protects, what it does not, and the trust boundaries.

  • Choose a variant

    SE050, SE051 or SE052, which applet and which authentication.

What you get¶

  • Layers with one job each. Link, APDU, secure channel, capability gate, objects, device, facade. See Architecture.
  • Errors you can act on. Every call returns Result<T> with an Error and the chip's status word. See the API guide.
  • A gate before the bus. A command the chip lacks never reaches it. See Contract.
  • No foot-guns. Irreversible operations are separate types behind named confirmations, compiled out by default. See Safety rules.
  • Honest about doubt. Every open question has a knob. See Ambiguities.
  • No heap, no exceptions, no RTTI. See Contract.
  • Tested without hardware. The tests run the driver against an independent model of the chip. See Testing and CI.

Certificates (PKI)¶

se05x::pki is an optional layer for the device side of a public key infrastructure: it asks for a certificate for a key that lives in the chip, stores the certificate the CA issues so nobody can change it, and checks a certificate chain up to a trust anchor you choose. It allocates nothing, throws nothing, and works only in buffers you pass in.

It is opt-in: #include "se05x_pki.hpp". The umbrella header se05x.hpp does not include it, and nothing else in the driver depends on it.

Figure description and sources

Left to right, top row once in the factory, bottom row at every boot. 1. The chip generates the key pair; only the public key comes out (ReadPublicKey). 2. BuildCsr writes the request and the chip signs its digest (DeviceSigner); VerifyCsr checks it against its own key. 3. The CA, outside the driver, issues the certificate. 4. StoreCertificate writes the certificate and the CA certificate (the trust anchor) into new binary objects with read-only policies, in one WriteBinary each, and reads them back. At boot: ReadCertificate and LoadTrustAnchor read them, VerifyChain checks signature, names, time, constraints and path length with the caller's clock, and the verified key is the chip's own. The CA, revocation and TLS are outside the driver.

Drawn from: inc/se05x_pki_csr.hpp; inc/se05x_pki_device.hpp; inc/se05x_pki_verify.hpp; figure module docs/diagrams/figures/pki-provisioning.py.

What it does and what it does not do¶

It does It does not
Write and read DER strictly (der::Writer, der::Reader) Accept BER: indefinite lengths, long forms for short lengths, multi-byte tags
Build PKCS#10 requests (RFC 2986) signed by a chip key (DeviceSigner) or a crypto-port key (PortSigner) Generate or hold a private key on the host
Parse X.509 v3 certificates with ECDSA P-256 / P-384 keys and Ed25519 keys Parse RSA, other curves, v1 or v2 certificates
Verify a chain to your trust anchors: signatures, names, time, basic constraints, key usage, path length Check revocation (CRL, OCSP), certificate policies, name constraints or extended key usage
Store certificates and trust anchors in binary objects with read-only policies, and read them back Act as a CA, run a TLS stack, or talk to a cloud service

Anything outside the profile is refused with a reason, never skipped: an unknown critical extension, a GeneralizedTime before 2050, a duplicate extension, a parameter where RFC 5758 says none, a compressed point.

Provisioning recipe¶

The four steps below are compiled for a board and run against the chip model in the tests (tests/docs/pki_recipes.hpp, tests/test_pki_recipes.cpp). Run them with platform SCP03 open (HRoT cookbook): the key policy requires secure messaging.

1. Generate the key in the chip¶

/// Step 1: generate the device key inside the chip and read its public half. The policy lets
/// anybody sign with it under secure messaging and nobody write, delete or regenerate it.
template <AppletGeneration G, PortSet P>
Result<pki::PublicKey> GenerateDeviceKey(se05x::Device<P>& device, ObjectId key,
                                         std::span<uint8_t, 65> public_key) noexcept {
  const Result<Policy> policy = PolicyBuilder<G, ObjectClass::EcKeyPair, Profile::Strict>{}
                                    .ForAllOthers()
                                    .template Allow<Rule::Sign>()
                                    .template Forbid<Rule::Write>()
                                    .template Forbid<Rule::Delete>()
                                    .template Forbid<Rule::Gen>()
                                    .RequireSecureMessaging()
                                    .Build();
  if (!policy.ok()) {
    return Result<pki::PublicKey>::Failure(policy.error, policy.detail);
  }
  if (const auto made = device.GenerateEcKey(key, policy.value, EcCurve::NistP256); !made.ok()) {
    return Result<pki::PublicKey>::Failure(made.error, made.detail);
  }
  return pki::ReadPublicKey(device, key, pki::KeyType::EcP256, MutableByteSpan{public_key});
}

2. Ask for a certificate¶

The chip signs the SHA-256 digest of the request info. VerifyCsr() then checks the request with the public key in it: a key id that does not belong to that public key is caught here, before the request reaches a CA.

/// Step 2: a certification request for that key, signed by the chip, with the chip's unique id
/// as the subject's serialNumber. The request is checked against its own key before it leaves.
template <PortSet P, typename Crypto>
Result<std::size_t> MakeCsr(se05x::Device<P>& device, Crypto& crypto, ObjectId key,
                            const pki::PublicKey& public_key, ByteSpan unique_id,
                            MutableByteSpan csr) noexcept {
  constexpr std::array<uint8_t, 6> kOrganization{0x44U, 0x65U, 0x76U, 0x69U, 0x63U, 0x65U};
  pki::Name subject{};
  static_cast<void>(subject.Add(pki::Attribute::Organization, ByteSpan{kOrganization})
                        .AddHex(pki::Attribute::SerialNumber, unique_id));
  const pki::CsrRequest request{&subject, public_key, nullptr, pki::key_usage::kDigitalSignature};
  pki::DeviceSigner<P> signer(device, key, pki::KeyType::EcP256);
  const Result<std::size_t> built = pki::BuildCsr(request, signer, crypto, csr);
  if (!built.ok()) {
    return built;
  }
  pki::PortVerifier<Crypto> verifier(crypto);
  const auto checked = pki::VerifyCsr(ByteSpan{csr}.first(built.value), verifier, crypto);
  return checked.ok() ? built : Result<std::size_t>::Failure(checked.error, checked.detail);
}

Text values are UTF-8 bytes: the layer never converts characters. Name::AddHex() writes bytes (the chip's unique id) as upper-case hex. countryName and serialNumber are PrintableString (X.520), every other attribute UTF8String (RFC 5280 4.1.2.6). Ask for a subjectAltName with AltNames (DNS name, URI, e-mail, IP address).

3. Store the certificate and the trust anchor¶

/// Step 3: store the certificate the CA issued, and the CA's certificate as the trust anchor,
/// each in a new binary object nobody can write; `admin` may delete them to rotate.
template <AppletGeneration G, PortSet P>
Result<void> ImportCertificates(se05x::Device<P>& device, ObjectId certificate, ByteSpan issued,
                                ObjectId anchor, ByteSpan ca_certificate,
                                AuthObject admin) noexcept {
  const Result<Policy> policy = pki::CertificatePolicy<G>(admin);
  if (!policy.ok()) {
    return Result<void>::Failure(policy.error, policy.detail);
  }
  std::array<uint8_t, 1024> scratch{};
  const auto stored_anchor =
      pki::StoreCertificate(device, anchor, ca_certificate, policy.value, scratch);
  if (!stored_anchor.ok()) {
    return stored_anchor;
  }
  return pki::StoreCertificate(device, certificate, issued, policy.value, scratch);
}

StoreCertificate() follows four rules, and refuses before sending anything when one fails:

  • the certificate must parse;
  • the policy must not grant Write to anyone, nor Delete to everybody (PolicyAllowsWrite): a policy is fixed when the object is created, so a read-only policy locks the content;
  • the certificate must fit one WriteBinary command, because a read-only object cannot take a second write: at most MaxStoredCertificate(policy) bytes, 999 with CertificatePolicy() and 990 with an administrator (ObjectTooLarge);
  • an existing object is never overwritten (ObjectExists).

It then reads the object back and compares it (ReadBackMismatch). To rotate a certificate, give CertificatePolicy() an administrator: that session may delete the object, and a new one is stored.

4. Check the chain at every boot¶

/// At every boot: read the certificate and the anchor back and verify the chain at `now` (Unix
/// seconds from a clock you trust). The verified key is the one the chip signs with.
template <PortSet P, typename Crypto>
Error CheckDeviceCertificate(se05x::Device<P>& device, Crypto& crypto, ObjectId certificate,
                             ObjectId anchor, uint64_t now) noexcept {
  std::array<uint8_t, 1024> anchor_bytes{};
  std::array<uint8_t, 1024> cert_bytes{};
  const auto trusted = pki::LoadTrustAnchor(device, anchor, anchor_bytes);
  const auto cert = pki::ReadCertificate(device, certificate, cert_bytes);
  if (!trusted.ok() || !cert.ok()) {
    return trusted.ok() ? cert.error : trusted.error;
  }
  const std::array<ByteSpan, 1> chain{cert.value.der};
  const std::array<pki::TrustAnchor, 1> anchors{trusted.value};
  pki::PortVerifier<Crypto> verifier(crypto);
  const pki::VerifyOptions options{now, pki::key_usage::kDigitalSignature, false};
  const auto verified =
      pki::VerifyChain(std::span<const ByteSpan>{chain}, std::span<const pki::TrustAnchor>{anchors},
                       options, verifier, crypto);
  return verified.error; // AttestationInvalid: pki::ReasonOf(verified.detail) says why
}

The time is yours: Unix seconds from a clock you trust. A time of 0 is refused (NoTime); the check is never skipped. A device that has no trustworthy time yet must get one first: a wrong clock makes an expired certificate look valid.

Chain verification¶

VerifyChain(chain, anchors, options, verifier, hasher) takes the chain end entity first, without the anchor, at most kMaxChain (6) certificates, and up to kMaxAnchors (8) anchors. From the anchor down it checks (RFC 5280 6.1):

Check Reason when it fails
Each certificate parses under the profile the parser's reason
The issuer is the subject above, byte for byte NameMismatch
The signature verifies with the key above; P-256 with ecdsa-with-SHA256, P-384 with ecdsa-with-SHA384 SignatureInvalid, AlgorithmMismatch
now is within notBefore and notAfter, both included NotYetValid, Expired
Every issuing certificate has cA TRUE, and keyCertSign when it has a keyUsage NotCa, KeyCertSignMissing
No more intermediates than any pathLenConstraint above (and the anchor's) allows PathLengthExceeded
The end entity has options.required_key_usage and is no CA unless allow_ca_leaf LeafKeyUsageMissing, LeafIsCa

Every intermediate counts toward the path length, self-issued or not: stricter than RFC 5280 6.1.4 (l). Names are compared byte for byte, which a chain from one CA meets; a CA that re-encodes names is refused (NameMismatch).

The verifier is a port: SignatureVerifier verifies a fixed-width r || s over a digest. PortVerifier<C> adapts any crypto port and verifies P-256 (the port's EcdsaP256Verify); a P-384 chain needs a verifier that supports P-384, or it is refused (CurveNotSupported). The digest comes from the crypto port's Hash. Ed25519 signatures are not verified by this layer (UnsupportedAlgorithm).

Errors¶

Every call returns a Result. When the PKI layer refuses, Detail::layer is Layer::Pki and pki::ReasonOf(detail) names the rule; pki::ToString(reason) gives its name. The coarse Error is:

Error Reasons
InvalidArgument malformed DER, a field outside the profile, a bad builder argument, NoTime
Unsupported a version, algorithm, curve or critical extension the layer does not handle; CurveNotSupported
AttestationInvalid a chain check failed: NameMismatch to LeafIsCa
BufferTooSmall BufferTooSmall, ObjectTooLarge
CryptoFailure the crypto port or a signer failed

A failure of the device (the bus, a status word, the capability gate) keeps the device's own Error and Detail.

Not verified on hardware¶

The chip model of the tests stores binary objects and P-256 keys only. On a real chip, still to be run on a bench:

  1. P-384: GenerateEcKey(id, policy, EcCurve::NistP384), ReadPublicKey(..., KeyType::EcP384, ...) returns 97 bytes, a DeviceSigner request verifies with openssl req -verify.
  2. Ed25519: the same with EcCurve::Ed25519 and KeyType::Ed25519 on SE050E or SE051; check that the public key read back and reversed (AN12543 7.1) is the one in the request, and openssl req -verify accepts it.
  3. A certificate of about 990 bytes stored with CertificatePolicy() reads back equal; a write to it is refused by the chip (PolicyDenied).

How it is tested¶

The vectors in tests/vectors/pki_vectors.hpp were made with OpenSSL from keys generated for that run and deleted; the requests use the published RFC 6979 and RFC 8032 test keys. The tests compare the request info byte for byte with OpenSSL's, build the Ed25519 request byte for byte, verify OpenSSL's chains, and check every refusal on an edited copy of a vector. Two libFuzzer targets (fuzz_pki_der, fuzz_pki_x509) check that the reader re-encodes every element it accepts to the same bytes and that the parser and the chain walk never accept what they should refuse. Each guard has a one-edit mutant in tools/mutants/pki.txt that the tests kill.

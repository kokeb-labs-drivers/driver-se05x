Ambiguities and knobs¶

Where the sources disagree or are missing, the driver does not guess silently. Each doubt below has a choice, a bench step that settles it, and a knob where one exists (Config fields and build flags; "model" knobs belong to the test chip model and only reproduce the case). The status column says whether the documents settle it (document and page named), partly settle it, or leave it open.

Corrections folded into the contract¶

  • A quiet chip answers within about 20 s, and up to 40 WTX requests are answered at session open. The old reference of 500 WTX is gone; Config::wtx_limit and kSessionOpenWtxAllowance carry the numbers.
  • GetFreeMemory returns 4 bytes on the SE052F only and 2 bytes elsewhere, SE051 7.x included.
  • SIGMA-I is not an SE05x feature. It is not in the command set.
  • Ed25519 and Montgomery values on the wire are the byte reverse of RFC 8032 and RFC 7748 (AN12543 pp. 168-170; an earlier note said little endian, which AN12543 corrects). A Montgomery ECDH with an inline public key writes NVM on every call.
  • On the SE050 and SE051, RST_N is the ISO 7816 reset and has no effect when only I2C is enabled (SE050 section 4.2, p. 9): there the reset port implements Reset() and PowerCycle() with ENA (VOUT wired to VCC) or a supply switch; the link only calls the port.

Still open¶

UM11225 was obtained (addendum 3). Both T=1 flavours are specified except the CRC byte order of the NXP flavour: the link accepts either order on the first valid frame and keeps it (A10). The code 0xC6 is a chip reset in the NXP flavour and RELEASE in the GP one. The GP flavour is specified by GPC_SPE_172 v1.0, but the SE052 data sheet selects a "GP 0.39" flavour, and the NAD and MPOT unit the chips use in it are open (A17, A32). The ECKey KDF is printed in AN12543 pp. 22-23 and 72-73 but has no vector: it is built behind a feature flag. The order of the attestation timestamp is settled (AN12543 3.9, p. 42: 4 persistent bytes, then 8 transient bytes, growing with every session open); the driver accepts only a timestamp later than the last one it accepted. The 6.x policy bit values, the SE052 configuration sheet and the SOT917 code stay open. The SEMS Lite update agent is outside v1.

Oracle vectors from the vendor middleware¶

tests/vectors/nxp_oracle_vectors.hpp holds vectors recorded by tools/oracle/build_oracle.sh against the pinned middleware checkout 7102413e, in a sandbox without network access (provenance and the BSD 3-Clause notice in tests/vectors/THIRD_PARTY.md). It records 122 commands, 62 on applet 7.2 and 60 on applet 3.x. tests/test_apdu_oracle_vectors.cpp builds each command with the same inputs and compares header and TLV body byte for byte; every remaining difference is listed there with its class and evidence (middleware quirks such as TAG_11 version 0 and TAG_2 FF; policy-less creates, which the library refuses, S-03; the WriteUserID instruction byte of the harness input; DeleteAll, below), and removing any one of them makes the test fail. The TLSPerformPRF P2 is no longer a difference: TlsPrfArgs::role gives the server role (AN12543 4.17.3), which the harness used. Framing is not compared: the middleware frames short case 4 without Le and extended commands as 00 LcH LcL ... 00 00. The structural check of tests/vectors/nxp_layouts.hpp (read from the source text by tools/oracle/extract_layouts.py) remains. The oracle covers 122 of the commands; the others rest on the APDU tables of AN12543 and AN12413 only. The ECKey key derivation, receipt and first MAC chaining value still rest on the independent chip model only (A15): that session stays behind its build flag.

DeleteAll: Lc 0x00 or case 1¶

AN12543 Table 339 prints the DeleteAll command with Lc 0x00, so the codec sends 80 04 00 2A 00; the middleware sends case 1 (80 04 00 2A, four bytes). Read as ISO/IEC 7816-4 the trailing byte is an Le, which the chip ignores for a command without a response, so both should be accepted. Not verified on hardware: a trace of DeleteAll on a real chip (bench step: run it in a RESERVED_ID_FACTORY_RESET session on a dev kit and record the C-APDU and the status word) decides it.

Attested read under secure messaging¶

A format 2 attestation signs the hash of "the complete APDU except the Le bytes" (AN12543 3.2.7.2, p. 19). Inside platform SCP03 or an AESKey session the applet sees the command after the secure channel unwrapped it, and the documents do not say which length form it then hashes. The driver hashes the unwrapped command with the shortest Lc form (one byte for up to 255 bytes, no Le), which is how the chip model rebuilds a command after unwrapping; outside secure messaging it hashes the command exactly as sent (Device::ReadVerified, detail::ShortestLcForm). A wrong choice fails closed: every attestation is refused with AttestationInvalid, nothing false is accepted. Not verified on hardware: bench step: run hrot::Device::Attest() under platform SCP03 on a dev kit; if it fails while the same read without secure messaging passes, the chip hashes the extended form.

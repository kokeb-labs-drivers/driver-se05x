Detailed Description

The "easy root of trust" facade: identity, keys by slot, sign, verify, ECDH, attest, stored data and certificates, monotonic counters, random numbers, the APDU budget and a transaction scope.

The facade is a small, hard-to-misuse layer over se05x::Device. Each common job of a hardware root of trust is one call with a typed result:

  • Objects are named by typed slots (Slot for keys, DataSlot, CounterSlot, CertSlot), so a data slot cannot be passed where a key slot is meant: it does not compile. Each kind maps to its own id range kObjectBase | kind << 8 | index (user ids, never a reserved one).
  • Keys are Key<U> values typed by their use (SignKey, AttestKey, AgreeKey, TlsKey, VerifyKey); only the facade creates a valid one, and each call takes only the key type it is for: Sign() does not accept an AgreeKey. Keys are NIST P-256, generated inside the chip (Origin::Internal); a key handle never holds key material.
  • Policies are built by the strict profile only (S-03): every facade key forbids write, delete and generate, and requires secure messaging; a counter forbids delete. A facade key or counter can therefore never be deleted or replaced; only a factory reset (irreversible::DeleteAllObjects) removes it. Each policy names the default session (authentication object 0) and, when the facade runs inside an AESKey or ECKey session, that session's credential too: id 0 does not cover other sessions (AN12543 3.7.1.2 p. 36), so an object used from another session is refused by the chip (fail closed, docs/ambiguities.md A20).
  • A call whose result the caller acts on (a key, a counter, a verification) needs authenticated answers: a secure-messaging layer with R-MAC (Device::AnswersAuthenticated()). A call that moves a secret (ECDH, Protection::Secret data) needs encryption both ways as well (Device::TrafficConfidential()). Otherwise the facade refuses with PolicyDenied (layer Hrot) and sends nothing (S-14): over a bus that can be probed, an unauthenticated answer could be forged, and an unencrypted one read.
  • A value read with an attestation comes back only as Verified<T>, a type that exists only after the signature, the freshness, the timestamp order and the unique identifier have been checked (S-04, S-09).
  • The facade cannot reach an irreversible operation: there is no path from here to irreversible::Operations.
  • Every call is counted against the APDU budget (S-17, ApduBudget): a call is admitted only when its worst-case APDU count (cost) fits under the chip's throughput ceiling, else it is refused with ThroughputLimited (layer Hrot) before anything is sent. One path sends more than the admitted cost: when the chip answers SW 0x66A6 anyway, the device resets it and selects the applet again, which sends up to four APDUs (the select, the lifecycle read and, with platform SCP03, the two handshake commands). They are counted in Used(), and the call sends nothing after them, so one call ends at most four APDUs past the ceiling.
  • The facade needs applet 7.x (SE050E, SE051, SE052). On applet 3.x (SE050 A to D, F) and 6.x (SE051 on early boards, OEF A564 and A565) every call returns Unsupported before anything is sent, after its argument checks (an invalid key, an off-curve point or an empty buffer is refused first with InvalidArgument): AN12413 has no plain attribute read, so a key or counter made on 3.x could never be adopted again after a reboot, and applet 6.x has no specification in hand. Use se05x::Device directly on 3.x and 6.x.

Certificates: the facade stores and reads the bytes only. Parsing, building and verifying DER, X.509 and PKCS#10 is the optional se05x::pki layer; the integration point is the trusted public key of TrustAttestationKey(), which should come from a certificate that layer verified.

Rules S-01 to S-17 are in docs/safety.md; the jobs, with compiled examples, in docs/getting-started.md and docs/hrot-cookbook.md.

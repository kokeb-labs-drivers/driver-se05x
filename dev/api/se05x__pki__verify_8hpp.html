Detailed Description

Certificate chain verification up to a caller's trust anchor (an RFC 5280 section 6 subset), with ECDSA P-256 and P-384 through a verifier port.

VerifyChain() takes the chain end entity first, without the trust anchor, and the anchors the caller trusts (a name and a key, TrustAnchor), and checks, from the anchor down (RFC 5280 6.1.3 and 6.1.4):

  • each certificate parses under the profile of ParseCertificate() (an unknown critical extension is refused there);
  • its issuer is, byte for byte, the subject of the certificate above it (or of the anchor);
  • its signature verifies with the key above it: ecdsa-with-SHA256 with a P-256 key, ecdsa-with-SHA384 with a P-384 key (another pairing is AlgorithmMismatch; Ed25519 signatures are UnsupportedAlgorithm);
  • the caller's time lies in its validity, both ends included (a time of 0 is NoTime: the check is never skipped);
  • every certificate above the end entity has basicConstraints cA TRUE, keyCertSign when it has a keyUsage, and the path length allowed by every pathLenConstraint above it (and by the anchor's) is not exceeded; each intermediate counts, self-issued or not (stricter than 6.1.4 (l));
  • the end entity has the key usage bits the options require, and is not a CA unless allowed.

Not checked (out of scope; say so where it matters): revocation (CRL, OCSP), certificate policies, name constraints (a CA with a critical nameConstraints is refused at parse time), extended key usage (reported in Certificate::ext_key_usage), the anchor's own validity.

The verifier port (SignatureVerifier) verifies a raw r || s over a digest; PortVerifier adapts any CryptoPort (P-256 only, the port's EcdsaP256Verify). A P-384 chain needs a verifier that supports P-384 (a hardware engine or a vetted library behind the same concept).

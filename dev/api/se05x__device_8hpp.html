Detailed Description

Device<P>: the command layer. Opens the chip, derives its capabilities, runs sessions and executes applet commands through the capability gate.

A command is a Command enumerator; its argument and reply types are CommandTypes<C>. Execute<C>() checks the state, runs the capability gate (gate::Check), the role check (RequiredRole), the policy generation and the argument limits the codec cannot see (the curve, the 919-byte EdDSA input of a UserID session, the UserID credential rules), encodes through Codec<C>, sends through the transport stack, maps the status word in the context of the command (apdu::StatusToError) and decodes the reply. A refusal sends nothing. Every method returns a Result; nothing throws, nothing allocates.

The transport stack (se05x_device_stage.hpp): the link; platform SCP03 over it when the device opened it (then every applet command goes through it, and never in the clear again until Close()); one applet session at a time over that (UserID, AESKey or ECKey). So an applet session inside platform SCP03 is two secure-messaging layers, each with its own keys and counters.

Commands that the device runs itself (detail::IsDeviceOwned: the select, the session handshake steps, TriggerSelfTest) and the irreversible ones do not compile through Execute<C>(). Irreversible commands run only through ExecuteIrreversible<C, Op>(), which exists only when kIrreversibleEnabled and needs Confirmation<Op> (S-10) and the session role of the command: SetLockState RESERVED_ID_TRANSPORT, SetPlatformScpRequest RESERVED_ID_PLATFORM_SCP, SetAppletFeatures RESERVED_ID_FEATURE, DeleteAll RESERVED_ID_FACTORY_RESET, DisableObjCreation RESERVED_ID_RESTRICT (AN12543 4.6.1 to 4.6.5); any other role is refused with ConditionsNotSatisfied before anything is sent. The answer of DeleteAll is not secure-messaging wrapped (AN13030), so the session ends with it.

Failures and recovery:

  • SW 0x66A6 (ThroughputLimited, S-17): the device drops every session (sending nothing), resets the chip once through the ladder (t1::Rung::ChipReset), selects the applet again, opens platform SCP03 again when it was open, and returns ThroughputLimited without repeating the command. It never resets twice for one call: a 0x66A6 to the select after the reset leaves the device NeedsReopen.
  • A secure-channel or transport failure under a session or platform SCP03 ends the stack: the device is NeedsReopen and refuses commands with NeedsReselect until Recover() selects the applet again (and opens platform SCP03 again). A plain Timeout without a session keeps the device Ready: the link resynchronises before the next command.
  • A session handshake that fails after CreateSession leaves a half-open session the chip cannot close (AN12543 3.6.5, errata APP.2): the device selects the applet again before it returns.
  • Close() and DeepPowerDown() are never refused for an uncertain state (RD-05).

Every wait is bounded by the link (S-05); the device adds no wait of its own and runs at most two selects and one chip reset per call.

Threading: one Device is not thread safe (S-11); the caller serialises, or uses the facade's transaction scope. Memory: the device holds its command and response buffers and four secure-messaging pipes (platform, AESKey, ECKey, UserID), about 11 KiB, as members (RD-06).

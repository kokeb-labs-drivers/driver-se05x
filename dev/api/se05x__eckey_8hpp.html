Detailed Description

The ECKey session: an applet session authenticated with an EC key, with SCP03 secure messaging under keys from ECDH.

Written from AN12543 3.6.3.3 (pp. 33-34), 4.5.4.1 (Tables 85 to 88, pp. 72-73) and 3.2.9 (pp. 22-23); AN12413 3.4.3 says the same for applet 3.x.

The flow: the caller reads the chip's ECKA public key once with an attested ReadObject of RESERVED_ID_ECKEY_SESSION and verifies it (not this layer). Open() then runs CreateSession for the credential, makes an ephemeral P-256 key pair on the host, signs SHA-256 of the TLVs 0xA6 (applet AID, SCP id 0xAB with parameters 01 and the level, key type 0x88, key length 0x10) and 0x7F49 (0xB0 the ephemeral public point, 0xF0 curve 03) with the host key, and sends ECKeySessionInternalAuthenticate (CLA 84, INS 88) inside the session. The chip answers a 16-byte random DR.SE (tag 0x85) and a 16-byte receipt (tag 0x86). Both sides compute:

  • shared secret Z = x(eSK.host * PK.SE.ECKA) (the ephemeral key is released right after);
  • master key = the first 16 bytes of SHA-256(00000001 || Z || DR.SE || 01 || level || 88 || 10);
  • S-ENC, S-MAC, S-RMAC = SCP03 KDF of the master key with constants 04, 06, 07, L = 128 and no context (AN12543: CMAC(MK, 00..00 04 00 00 80 01) and so on);
  • receipt = CMAC(S-RMAC, the 0xA6 and 0x7F49 TLVs), checked with ct::Equal (A15);
  • the encryption counter starts at 1.

Not in AN12543, taken from the middleware read as an oracle: the first MAC chaining value is the SCP03 KDF of the master key with constant 08 and L = 128; the authentication payload is the bare TLVs (Figure 14), not wrapped in TAG_1 as Table 85 suggests; the signature is DER encoded.

Behind a feature flag. No end-to-end vector of a real chip or of the middleware exists yet, so the session is compiled with SE05X_ENABLE_ECKEY_SESSION (default 0): without it Open() returns Unsupported and sends nothing. The engine (eckey::detail::Engine) is always built and tested against the independent model, so turning the flag on changes no code path but the gate.

Secrets: the shared secret and the master key exist only inside one call (wiped, released); the session keys are KeyRef handles of the crypto port. A session never survives a link reset or a failed response check (S-07, S-15).
